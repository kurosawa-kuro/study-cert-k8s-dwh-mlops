# KCNA クラスタ内部アーキテクチャ ― 概念理解ガイド

*対象：CKAD 合格者（YAML操作・kubectl操作は習得済み）が
KCNA で「なぜそうなるのか？」を体系的に理解するためのガイド*

---

## 1. CKAD から KCNA への視点転換

| CKAD での学習内容 | KCNA での追加理解 |
|------------------|------------------|
| `kubectl apply -f pod.yaml` | **なぜ** Pod が作成されるのか？ |
| `kubectl get pods` | **どのコンポーネント**が Pod 状態を管理しているか？ |
| `kubectl describe pod` | **どこで** イベントが生成されるのか？ |

---

## 2. コントロールプレーン主要コンポーネント（KCNA 重点）

| コンポーネント | KCNA での理解ポイント | 試験での問われ方 |
|---------------|---------------------|----------------|
| **API Server** | REST API の単一入口点<br>認証・認可・Admission Control | 「Pod 作成リクエストの最初の処理者」 |
| **etcd** | クラスタの「真実の源」<br>全てのオブジェクトの永続化 | 「etcd が停止したら何が起こる？」 |
| **Scheduler** | **未割り当て** Pod に Node を決定 | 「Pending Pod が動かない理由」 |
| **Controller Manager** | 宣言的状態と実際の状態を同期 | 「Deployment が ReplicaSet を作る理由」 |

---

## 3. ノード側コンポーネント（CKAD 未習得部分）

| コンポーネント | CKAD では触れない部分 | KCNA での理解 |
|---------------|---------------------|---------------|
| **kubelet** | Node 上の Pod ライフサイクル管理<br>CRI との連携 | 「Pod が実際に起動する仕組み」 |
| **Container Runtime** | containerd/CRI-O の役割<br>コンテナの実際の起動 | 「コンテナランタイムの選択基準」 |
| **kube-proxy** | Service のネットワーク実装<br>iptables/ipvs の使い分け | 「Service が Pod に転送される仕組み」 |

---

## 4. Pod 作成フロー（概念理解）

```
1. kubectl apply → API Server
   ↓
2. API Server → etcd (永続化)
   ↓
3. Scheduler が WATCH → Node 決定
   ↓
4. kubelet が WATCH → Pod 起動
   ↓
5. Container Runtime → コンテナ実行
```

**KCNA ポイント**：各ステップで「何が失敗する可能性があるか？」

---

## 5. KCNA 試験対策 ― 3つの理解レベル

### Level 1: コンポーネント識別
- 「Pod が Pending のまま → Scheduler の問題」
- 「etcd エラー → クラスタ全体の障害」

### Level 2: 因果関係理解
- 「API Server 停止 → kubectl 全コマンド失敗」
- 「kubelet 停止 → その Node の Pod 全停止」

### Level 3: 設計判断
- 「高可用性 → etcd クラスタ化」
- 「スケーラビリティ → API Server 水平スケール」

---

## 6. CKAD 経験者が陥りがちな誤解

| 誤解 | 正しい理解 |
|------|-----------|
| 「kubectl が直接 Pod を作る」 | 「API Server 経由で etcd に保存」 |
| 「Scheduler が Pod を起動する」 | 「Scheduler は Node 選択のみ」 |
| 「Controller が Pod を管理する」 | 「Controller は ReplicaSet などを管理」 |

---

## 7. KCNA 頻出問題パターン

### 7-1. コンポーネント責任分離
```
Q: Pod が Running にならない原因として、
   最も可能性が高いコンポーネントは？
A: kubelet（実際の Pod 起動を担当）
```

### 7-2. 障害影響範囲
```
Q: etcd が停止した場合の影響は？
A: 新規オブジェクト作成不可、既存 Pod は継続動作
```

### 7-3. 設計原則
```
Q: なぜ API Server が単一入口点なのか？
A: 認証・認可・監査の一元化
```

---

## 8. 学習の優先順位

### 高優先度（KCNA 必須）
1. **API Server の役割** ― 全てのリクエストの入口
2. **etcd の重要性** ― クラスタの真実の源
3. **Scheduler の動作** ― Pod 配置の決定者

### 中優先度（理解を深める）
1. **Controller Manager** ― 宣言的状態の実現者
2. **kubelet** ― Node 上の Pod 管理者

### 低優先度（CKAD で習得済み）
1. kubectl コマンド操作
2. YAML マニフェスト作成

---

## 9. セルフチェック（CKAD 経験者向け）

### 理解度確認
1. **Pod 作成時に etcd に何が保存される？**
   - Pod オブジェクトの完全な定義
   - メタデータ、spec、status

2. **Scheduler が Node を選ぶ基準は？**
   - リソース可用性（CPU/メモリ）
   - Node の Taint/Toleration
   - Pod の NodeSelector/Affinity

3. **kubelet が Pod を起動できない理由は？**
   - イメージ pull 失敗
   - リソース不足
   - セキュリティポリシー違反

---

## 10. まとめ

**CKAD から KCNA への学習方針**：
- **操作スキル** → **理解スキル** への転換
- **What** → **Why** への視点移動
- **個別機能** → **全体アーキテクチャ** への理解

**KCNA 合格の鍵**：
- 各コンポーネントの「責任範囲」を明確に理解
- 「障害時の影響範囲」を即答できる
- 「設計原則」の背景を説明できる
