## 2. コンテナ技術の基盤（KCNA 重点）

### 2-1. Linux カーネル機能

| 技術 | CKAD では触れない部分 | KCNA での理解 |
|------|---------------------|---------------|
| **Namespaces** | プロセス・ネットワーク・マウントの分離 | 「コンテナ間の分離メカニズム」 |
| **cgroups** | CPU・メモリ・ディスクI/O の制限 | 「リソース制限の実装方法」 |
| **chroot** | ファイルシステムの分離 | 「ルートディレクトリの変更」 |

### 2-2. コンテナランタイムの役割

| ランタイム | CKAD では触れない部分 | KCNA での理解 |
|-----------|---------------------|---------------|
| **containerd** | OCI 標準の実装<br>CNCF プロジェクト | 「Kubernetes のデフォルトランタイム」 |
| **CRI-O** | Kubernetes 専用<br>軽量設計 | 「Red Hat 系の推奨ランタイム」 |
| **Docker** | 従来のデファクト<br>現在は containerd 使用 | 「歴史的経緯と現在の位置づけ」 |

## 3. OCI (Open Container Initiative) 標準

### 3-1. OCI の意義

**CKAD では習得済み**：
- Dockerfile の書き方
- イメージのビルド・プッシュ

**KCNA で追加理解**：
- **標準化のメリット** ― ベンダー非依存
- **相互運用性** ― 異なるツール間での互換性
- **エコシステム** ― 共通の基盤による発展

### 3-2. OCI 標準の構成要素

| 要素 | 役割 | KCNA での理解 |
|------|------|---------------|
| **Image Spec** | コンテナイメージの形式定義 | 「tar ファイル + JSON マニフェスト」 |
| **Runtime Spec** | コンテナ実行時の仕様 | 「起動パラメータの標準化」 |
| **Distribution Spec** | イメージ配布の仕様 | 「レジストリ間の互換性」 |

## 4. コンテナセキュリティ（KCNA 重点）

### 4-1. セキュリティモデル

| 観点 | CKAD では触れない部分 | KCNA での理解 |
|------|---------------------|---------------|
| **特権分離** | root ユーザーの制限<br>capabilities の制御 | 「コンテナの最小権限原則」 |
| **リソース制限** | cgroups による制限<br>ulimit の設定 | 「リソース枯渇攻撃の防止」 |
| **ファイルシステム** | 読み取り専用ルート<br>tmpfs の活用 | 「不変インフラの実現」 |

### 4-2. セキュリティベストプラクティス

**KCNA で問われるポイント**：
- **非 root ユーザー**での実行
- **最小限の capabilities** 付与
- **読み取り専用**ファイルシステム
- **リソース制限**の設定

## 5. コンテナオーケストレーションとの関係

### 5-1. Kubernetes での位置づけ

| レイヤ | 役割 | KCNA での理解 |
|--------|------|---------------|
| **Kubernetes** | オーケストレーション<br>スケジューリング | 「コンテナの管理・運用」 |
| **CRI** | コンテナランタイムインターフェース | 「Kubernetes とランタイムの橋渡し」 |
| **OCI** | コンテナ標準 | 「基盤となる技術仕様」 |

### 5-2. CRI (Container Runtime Interface)

**CKAD では習得済み**：
- `kubectl run` での Pod 作成
- コンテナの起動・停止

**KCNA で追加理解**：
- **CRI の役割** ― Kubernetes とランタイムの分離
- **プラグイン方式** ― 異なるランタイムの切り替え
- **標準化のメリット** ― ベンダー非依存の実現

### Level 3: 設計判断
- 「セキュリティ要件 → 適切なランタイム選択」
- 「運用要件 → コンテナ設計方針」
