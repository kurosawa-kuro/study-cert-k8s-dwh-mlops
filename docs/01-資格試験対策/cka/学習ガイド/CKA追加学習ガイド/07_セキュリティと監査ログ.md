# 07_セキュリティと監査ログ

## CKAD合格者向け セキュリティ・監査ログ理解ガイド

### 視点の転換

| 観点 | CKADでの理解 | CKAでの追加理解 |
|------|--------------|----------------|
| セキュリティ | アプリケーションレベルの設定 | クラスタ全体のセキュリティ体制 |
| 認証・認可 | ServiceAccount と RBAC の基礎 | 統合認証と高度な権限管理 |
| 監査 | 基本的なログ確認 | 包括的な監査証跡とコンプライアンス |
| 脅威対策 | コンテナセキュリティの基礎 | ランタイム保護と侵入検知 |

### 重点学習内容

| CKAD では触れない部分 | CKA での理解 |
|---------------------|-------------|
| API サーバー監査ログ | 監査ポリシーの設計と実装 |
| 統合認証（OIDC/LDAP） | 外部 IdP との連携 |
| Admission Controller の高度な活用 | セキュリティポリシーの強制 |
| ランタイムセキュリティ | Falco による脅威検知 |

### 学習目的

1. **包括的なセキュリティ戦略の実装**
   - Defense in Depth の考え方
   - ゼロトラストアーキテクチャ
   - 最小権限の原則の徹底

2. **監査とコンプライアンスの自動化**
   - 監査ログの設計と管理
   - コンプライアンス要件への対応
   - インシデント調査の効率化

3. **脅威の検知と対応**
   - 異常な動作の早期発見
   - 自動化された対応プロセス
   - セキュリティインシデントの事後分析

### 学習手順

#### 1. API サーバー監査ログの設定

```yaml
# 監査ポリシーの定義
apiVersion: audit.k8s.io/v1
kind: Policy
rules:
  # 機密リソースへのアクセスを詳細記録
  - level: RequestResponse
    omitStages:
      - RequestReceived
    resources:
      - group: ""
        resources: ["secrets", "configmaps"]
    namespaces: ["kube-system", "production"]
    
  # 認証失敗を記録
  - level: Metadata
    omitStages:
      - RequestReceived
    userGroups: ["system:unauthenticated"]
    
  # Pod の作成・削除を記録
  - level: Request
    verbs: ["create", "delete", "patch"]
    resources:
      - group: ""
        resources: ["pods"]
      - group: "apps"
        resources: ["deployments", "replicasets"]
    
  # RBAC 変更を詳細記録
  - level: RequestResponse
    resources:
      - group: "rbac.authorization.k8s.io"
        resources: ["roles", "rolebindings", "clusterroles", "clusterrolebindings"]
    
  # 読み取り操作は軽量記録
  - level: Metadata
    verbs: ["get", "list", "watch"]
    
  # その他は記録しない
  - level: None
```

#### 2. OIDC による統合認証

```yaml
# kube-apiserver の OIDC 設定
apiVersion: v1
kind: Pod
metadata:
  name: kube-apiserver
spec:
  containers:
  - command:
    - kube-apiserver
    - --oidc-issuer-url=https://auth.example.com
    - --oidc-client-id=kubernetes
    - --oidc-username-claim=email
    - --oidc-username-prefix=oidc:
    - --oidc-groups-claim=groups
    - --oidc-groups-prefix=oidc:
    - --oidc-ca-file=/etc/kubernetes/pki/oidc-ca.crt
---
# OIDC ユーザーの RBAC 設定
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: oidc-cluster-admins
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: cluster-admin
subjects:
- kind: Group
  name: oidc:platform-admins
  apiGroup: rbac.authorization.k8s.io
---
# 開発者向けの名前空間別権限
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-team-binding
  namespace: development
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: edit
subjects:
- kind: Group
  name: oidc:dev-team
  apiGroup: rbac.authorization.k8s.io
```

#### 4. Falco によるランタイムセキュリティ

```yaml
# Falco ルールの例
- rule: Unauthorized Process in Container
  desc: Detect unauthorized process execution in containers
  condition: >
    spawned_process and container and
    not proc.name in (allowed_processes) and
    not container.image.repository in (trusted_repos)
  output: >
    Unauthorized process started in container
    (user=%user.name command=%proc.cmdline container_id=%container.id
    image=%container.image.repository:%container.image.tag)
  priority: WARNING
  tags: [container, process, security]

- rule: Write below etc
  desc: Detect writes to /etc directory
  condition: >
    open_write and container and
    fd.name startswith /etc and
    not proc.name in (package_mgmt_binaries)
  output: >
    File write detected under /etc
    (user=%user.name command=%proc.cmdline file=%fd.name container_id=%container.id)
  priority: ERROR
  tags: [filesystem, container, security]

- rule: Outbound Network Connection
  desc: Detect outbound network connections from containers
  condition: >
    outbound and container and
    not fd.sip in (allowed_server_ips) and
    not proc.name in (allowed_network_binaries)
  output: >
    Outbound connection detected
    (user=%user.name command=%proc.cmdline connection=%fd.name container_id=%container.id)
  priority: NOTICE
  tags: [network, container]
```

### 演習アイデア

#### 演習1: 監査ログの分析

```bash
# 監査ログから特定の操作を抽出
# Secret へのアクセスを検索
jq -r 'select(.objectRef.resource == "secrets") | 
  "\(.timestamp) \(.user.username) \(.verb) \(.objectRef.namespace)/\(.objectRef.name)"' \
  /var/log/kubernetes/audit/audit.log

# 失敗した操作を検索
jq -r 'select(.responseStatus.code >= 400) | 
  "\(.timestamp) \(.user.username) \(.verb) \(.objectRef.resource) Status: \(.responseStatus.code)"' \
  /var/log/kubernetes/audit/audit.log

# 特定ユーザーの活動を追跡
jq -r 'select(.user.username == "suspicious-user") | 
  "\(.timestamp) \(.verb) \(.objectRef.resource)/\(.objectRef.name)"' \
  /var/log/kubernetes/audit/audit.log
```

#### 演習2: RBAC の最小権限設計

```yaml
# 開発者用の最小権限 Role
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: developer-minimal
  namespace: development
rules:
# Pod の読み取りと更新のみ
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
- apiGroups: [""]
  resources: ["pods/log"]
  verbs: ["get"]
# Deployment の管理
- apiGroups: ["apps"]
  resources: ["deployments"]
  verbs: ["get", "list", "watch", "create", "update", "patch"]
# ConfigMap の読み取りのみ
- apiGroups: [""]
  resources: ["configmaps"]
  verbs: ["get", "list", "watch"]
# Secret へのアクセスは不可
```

#### 演習3: セキュリティインシデント対応

```bash
# 1. 異常な Pod の特定
kubectl get pods -A -o json | jq -r '
  .items[] | 
  select(.spec.securityContext.privileged == true or
         .spec.hostNetwork == true or
         .spec.hostPID == true) |
  "\(.metadata.namespace)/\(.metadata.name) - Flags: privileged=\(.spec.securityContext.privileged) hostNetwork=\(.spec.hostNetwork) hostPID=\(.spec.hostPID)"
'

# 2. 監査ログから調査
SUSPICIOUS_POD="suspicious-namespace/suspicious-pod"
jq -r --arg pod "$SUSPICIOUS_POD" '
  select(.objectRef.resource == "pods" and 
         .objectRef.namespace + "/" + .objectRef.name == $pod) |
  "\(.timestamp) \(.user.username) \(.verb) \(.sourceIPs[0])"
' /var/log/kubernetes/audit/audit.log

# 3. Pod の隔離
kubectl label pod -n suspicious-namespace suspicious-pod quarantine=true
kubectl apply -f - <<EOF
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: quarantine-policy
  namespace: suspicious-namespace
spec:
  podSelector:
    matchLabels:
      quarantine: "true"
  policyTypes:
  - Ingress
  - Egress
EOF
```

### CKA試験での出題パターン

| パターン | 問題例 | 対策 |
|---------|--------|------|
| RBAC 設定 | 「特定の権限を持つ Role/RoleBinding を作成」 | verb と resource の組み合わせを理解 |
| ServiceAccount | 「Pod 用の ServiceAccount と権限設定」 | SA と RBAC の連携を練習 |
| セキュリティコンテキスト | 「セキュリティ要件を満たす Pod 作成」 | 必須セキュリティ設定の暗記 |

### CKAD経験者が陥りがちな誤解

| 誤解 | 正しい理解 |
|------|-----------|
| 「監査ログは自動で有効」 | API サーバーの明示的な設定が必要 |
| 「RBAC だけで十分なセキュリティ」 | 多層防御が必要（PSS、NetworkPolicy 等） |
| 「root ユーザーでの実行は避けられない」 | 適切な設計でほぼ全て非 root 化可能 |
| 「セキュリティは後から追加」 | 設計段階からの組み込みが重要 |

### 学習優先順位

| 優先度 | 項目 | 理由 |
|--------|------|------|
| 高 | RBAC の詳細設計 | CKA 試験の重要トピック |
| 高 | ServiceAccount の管理 | Pod のセキュリティ基礎 |
| 中 | 監査ログの基本設定 | トラブルシューティングに有用 |
| 低 | Falco 等の高度なツール | 概念理解で十分 |
